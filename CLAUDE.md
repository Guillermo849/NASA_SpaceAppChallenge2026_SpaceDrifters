# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Android app for the NASA Space Apps Challenge 2026, challenge "Create Health Monitoring Software for Astronauts on Space Missions" (team SpaceDrifters, 48 h hackathon, several people working in parallel). It is a prototype: not a medical device, all crew data is simulated. Respond to the user in Spanish (castellano). `README.md` (in Spanish) is the team-facing guide — keep it in sync when structure or conventions change.

Current state: shared skeleton (Gradle, theme, navigation, placeholder screens) plus the neurocognitive module in progress (steps 1–5 of its plan done) and the astronaut dashboard. **Single database**: `data/local/AppDatabase.kt` (team's schema, file `astronaut_health.db`, `AppDatabase.get(context)`; no migrations: bump `version`, destructive fallback) holds the team tables (`entity/`, `dao/`: app_user, mission, astronaut — extended with `crew_role` and `usual_sleep_hours` —, measurements, ECG, BP, clinical, alert/alert_threshold) plus ours: cognitive tables in `DatosCognitivos.kt` (`CognitivoDao`) and `registro_diario` in `DatosTripulacion.kt` (`TripulacionDao`, which also reads crew as the `Astronauta` projection from astronaut + mission). The team's neuro_test/neuro_result tables were dropped in favour of ours (trial-level detail, Earth delay, baseline). Our tables reference `astronaut.id` via `astronautaId` without FKs. The old `spacedrifters.db` file is deleted on start; Stroop and N-Back tests (instructions → practice only the first time → full-screen test → result phrase vs baseline); `data/repository/CognitivoRepository` saves session + trials + summary in one transaction, computes metrics/state (Java, `domain/cognitivo`) and recalculates baselines. Daily log (`RegistroDiario`: sleep hours, KSS sleepiness, symptoms) has its own screen; mission day comes from `mission.start_date`. Sample data: `assets/datos_ejemplo.json` describes each crew member (baseline, per-day deviation in SDs, sleep, symptoms); on first launch (empty DB) `data/ejemplo/CargadorDatosEjemplo` generates the trials (`domain/cognitivo/ejemplo`, Java) and saves them through `CognitivoRepository`, so summaries/states derive from trials. Mission day 14 = install day; to regenerate, clear the app's data. `DatosEjemploTest` pins the demo cases (Maya N-Back worsening + last session still in transit, Leo Stroop ALERTA today + headache, Ane/Ilan normal). Sample data also creates the mission, one ASTRONAUT `app_user` per crew member and their `astronaut` rows. Rule-based alerts (step 7): rules live in `assets/reglas.json` (`data/config/ReglasJson`), the pure engine in `domain/reglas` (Java, `MotorReglas`, tested in `MotorReglasTest`); `data/repository/AlertasRepository` builds the context (recent mission sessions, sleep, today's symptoms), runs the rules and stores alerts in the team's `alert` table (source NEURO; extra columns rule_id, priority, steps, explanation JSON = "Por qué ha saltado", assigned_astronaut_id, arrives_earth_at), skipping a rule that already has an ACTIVE alert. Rules are evaluated after saving a valid test or a daily log, and once after loading sample data. The astronaut dashboard shows active alerts ("Avisos"). Doctor (step 6): `ui/screens/medico` — crew list → astronaut profile (tab "Pruebas cognitivas": data in transit with countdown, per-test summary card + 30-day chart with real values, received alerts with "Por qué ha saltado" and Confirmar / Pedir otra prueba, actions Programar prueba extra / Recalcular línea base / Añadir nota, sessions table) → session detail with every trial. `data/repository/MedicoRepository` filters everything by arrival time on Earth; screens get models built by `construirPerfil` (MedicoUi.kt) and refresh every 30 s. Extra tests (`prueba_programada`) show in the astronaut's "Pruebas de hoy" until a valid session of that test is saved; notes in `nota_medica`. Sample-data alerts are generated at each astronaut's last session time, so they reach Earth with that data. The astronaut using the app is `AppContainer.astronautaActualId` (1 = Maya Okafor, provisional).
- Keep `AppDatabase` in **Kotlin**. With the `@Database` class in Java, Android Studio's editor flags every Kotlin use of it ("Cannot access 'RoomDatabase' which is a supertype of AppDatabase") even though Gradle builds fine (Room 2.8 is KMP). Team entities/DAOs in Java are fine.
- Mission config (Earth delay, Vigilar/Alerta thresholds in SDs, min baseline sessions) lives in `assets/config_mision.json` (read by `data/config/ConfigMision`), not in code.
- Physiological module (steps 1–4 of its plan done: data, engine, alarm signs + emergency screen, on-board medical officer): decision protocols as trees in `assets/protocolos.json` (`data/config/ProtocolosJson`; node types CONDICION/PRUEBA/DECISION/FIN, common alarm signs, protocol 5 "ambiental") run by the generic Java engine `domain/protocolos/MotorProtocolos` over named facts (`Hechos`: symptoms, vitals already compared with baseline, test results under the test name). Missing fact = wait (three-valued `Veredicto`). Alarm signs → level 5 from any node; levels 1–5 (`NivelGravedad`) only go up automatically, a lower node leaves `nivelPropuesto` until `confirmarNivel(..., confirmadoPor)`. Vital-sign thresholds (base ± % or points, OR absolute) in `assets/config_umbrales.json` (`data/config/ConfigUmbrales` → `domain/fisiologico/UmbralesFisiologicos` produces facts FC_ALTA, PAS_BAJA, SPO2_BAJA, TAQUIPNEA...). Room: `DatosFisiologicos.kt` (`protocolo_activo`, `evento_protocolo`, `prueba_clinica`, `balance_hidrico`, `FisiologicoDao`); `MeasurementType` gained `RR`. No medical logic in Kotlin: change the JSON. JVM tests (`ProtocolosTest`, `DetectorAmbientalTest`, `UmbralesFisiologicosTest`) read the real assets via `Assets.leer`. Step 3: `data/repository/FisiologicoRepository` (`activarEmergencia` moves every open protocol of the astronaut to node `EMERGENCIA` level 5, or opens a direct `emergencia` protocol; `marcarAtendida` closes them with `confirmadoPor`); `ui/screens/emergencia` — the astronaut panel has a fixed "Tengo un síntoma de alarma" button (`BotonAlarma`), and `CapaEmergencia` sits on top of `AppNavHost` in `MainActivity`, so the full-screen emergency shows over any screen and role until marked as handled (`EmergenciaFlujoTest`). Step 4: third role "Oficial médico de a bordo" in the role selector → `ui/screens/oficial` (open protocols of the crew with pending tests, current actions and the steps walked, current one marked → result form with closed options, or SV/CO numbers for the echo). `FisiologicoRepository.evaluar(astronautaId, Hechos)` opens/advances protocols and creates `prueba_clinica` rows for pending tests; `guardarResultado` saves a result and resumes the protocol from its node. `protocolo_activo` keeps the facts known so far (`hechos` JSON) and the path (`recorrido`). Results become facts in Java `domain/fisiologico/InterpretePruebas` (closed options per test, analytics altered, Doppler worse than the previous one, SV/CO vs their first echo or `referencias` in config_umbrales.json). Codes from protocolos.json get their text in `ui/components/TextosFisiologico.kt` (`InterpretePruebasTest` checks every node/action has one). Sample data (`CargadorDatosEjemplo`, needs a non-waiting `FisiologicoRepository`: use `AppContainer.cargadorDatosEjemplo()`) opens Leo P1 waiting for the blood tests and Maya P2 repeating vitals (`DatosEjemploTest`, `OficialMedicoFlujoTest`).

## Commands

Gradle wrapper (`./gradlew` in Bash, `.\gradlew` / `gradlew.bat` on Windows):

- Build: `./gradlew assembleDebug` · install on device/emulator: `./gradlew installDebug`
- Minimum check before pushing (per README): `./gradlew assembleDebug testDebugUnitTest`
- Unit tests (JVM, `app/src/test`): `./gradlew testDebugUnitTest`
- Single test: `./gradlew testDebugUnitTest --tests "com.example.nasa_spaceappchallenge2026_spacedrifters.ExampleUnitTest.suma_esCorrecta"`
- Instrumented tests (`app/src/androidTest`, needs device/emulator): `./gradlew connectedDebugAndroidTest`
- Lint: `./gradlew lintDebug`

## Build setup (non-obvious bits)

- AGP 9.2.1 with **built-in Kotlin**: do not apply `org.jetbrains.kotlin.android`. The Kotlin version is set by the `kotlin` entry in `gradle/libs.versions.toml` (compose + serialization compiler plugins).
- Gradle runs on JDK 21 (`gradle/gradle-daemon-jvm.properties`); bytecode targets Java 17.
- `compileSdk` 37 is required by Compose 1.12 / Lifecycle 2.11; `targetSdk` 36, `minSdk` 26 (java.time without desugaring).
- Room uses KSP (`ksp(libs.androidx.room.compiler)`), not kapt.
- All versions live in `gradle/libs.versions.toml`; repositories only in `settings.gradle.kts` (`FAIL_ON_PROJECT_REPOS`).
- `.idea/` is git-ignored on purpose (machine-specific).

## Architecture

Package root `com.example.nasa_spaceappchallenge2026_spacedrifters`:

- Single Activity (`MainActivity`) → `SpaceDriftersTheme` → `ui/navigation/AppNavHost`.
- Navigation Compose with **type-safe routes** (`@Serializable` objects/data classes in `ui/navigation/Rutas.kt`). Screens never receive the `NavController`; they get lambdas (`onAtras`, `onMedico`, ...) wired in `AppNavHost`.
- MVVM (ViewModel + StateFlow) with **manual DI**: `SpaceDriftersApp` owns an `di/AppContainer` (create DB/repositories there with `by lazy`); every ViewModel is registered as an `initializer { ... }` in `di/AppViewModelProvider.Factory`, using `CreationExtras.app()` to reach the container. No Hilt. A ViewModel lives next to its screen (`ui/screens/<zona>/XViewModel.kt`); the screen gets it with `viewModel<X>(factory = AppViewModelProvider.Factory)` and reads state via `collectAsStateWithLifecycle()`. Route arguments reach a ViewModel through `createSavedStateHandle().toRoute<Ruta>()` inside the initializer.
- Layers: `data/local` (Room entities/DAOs/AppDatabase) → `data/repository` → `ui/screens/<rol|astronauta|medico>`. Pure logic without Android (e.g. the planned JSON-driven rule engine) goes in `domain/` so it can be unit-tested on the JVM. `domain/cognitivo` is written in **Java** (team member's preference; UI and Room stay Kotlin): no coroutines there — test controllers (e.g. `ControladorStroop`) get timing through the `Temporizador` interface (ViewModel implements it with `viewModelScope` + `delay`; JVM tests use `TemporizadorFalso`) and report phases through a callback. Avoid Java records/sealed types; use final classes.
- Cognitive tests timing: stimulus onset = `withFrameNanos` frame time, response = pointer event `uptimeMillis` — both CLOCK_MONOTONIC so they can be subtracted (don't mix in `elapsedRealtimeNanos`). Test screens share `ui/components/PantallasPrueba.kt` (`ZonaRespuesta` records the touch instant, `InterrumpirAlSalir`, `MensajePrueba`) and apply `ModoPrueba` (full screen + keep screen on) from the instructions screen on, so Android's one-time "Viewing full screen" hint doesn't cover the timed test; nav routes have no transitions.
- Every screen wraps its content in `ui/components/PantallaBase`, which provides the top bar (back button when `onAtras != null`) and the mandatory "Prototipo, no es un dispositivo médico · Datos simulados" footer (`AvisoPrototipo`). Unfinished screens use `EnConstruccion(padding)` from the same file as placeholder content.
- Saving sessions: ViewModels save through `guardarEnSegundoPlano(AppContainer.ambitoAplicacion)` so a save (e.g. an interrupted test, `valida = false`) finishes even if the screen closes. Practice and interrupted sessions get no `ResumenSesion` and never count.
- Tests: instrumented UI tests (`androidTest/NavegacionTest.kt`) use `androidx.compose.ui.test.junit4.v2.createAndroidComposeRule<MainActivity>()` and look up nodes via `activity.getString(R.string.…)`, never hard-coded text, so they pass in either locale. Flow tests that touch Room add `@get:Rule(order = 0) val limpia = BaseDeDatosLimpia()` before the compose rule (`order = 1`) so they don't depend on each other. `StroopCompletoTest` runs a whole Stroop session (~1 min).
- Empty folders hold a `.gitkeep`; delete it when adding the first real file there.

## Conventions

- Code identifiers and UI text are in Spanish. All visible text goes in `res/values/strings.xml` (Spanish, default) **and** `res/values-en/strings.xml` (English, for the NASA submission).
- Fonts are bundled in `res/font` (works offline): Space Grotesk for display/headline/title, Inter for body/labels, JetBrains Mono for `labelMedium` (numbers). Set in `ui/theme/Type.kt` for every M3 style; use `MaterialTheme.typography`, not ad-hoc families. OFL license texts live in `assets/licencias/` and must ship with the fonts.
- App icon = adaptive vector (`drawable/ic_launcher_background|foreground|monochrome.xml`, no PNG mipmaps since minSdk 26); `drawable/ic_logo.xml` is the same logo cropped for in-app use. The Android 12+ splash (`values-v31/themes.xml`) shows that icon on `@color/fondo`. Non-Compose colors (`res/values/colors.xml`) mirror `Color.kt`.
- `PantallaBase(titulo = null)` hides the top bar (for screens with their own header, like the role selector); the prototype footer stays.
- Always-dark "mission control" theme; palette only in `ui/theme/Color.kt`. Use `MaterialTheme.colorScheme` and, for health states, `LocalEstadoColores`. States (Normal / Vigilar / Alerta / Sin datos) must never be conveyed by color alone — always with text; missing data is "Sin datos", never shown as fine.
- Touch targets ≥ 48 dp; every icon has a `contentDescription` from strings. Icons are local vector drawables in `res/drawable/ic_*.xml` (no material-icons dependency).
